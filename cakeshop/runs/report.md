### 1. OS command injection on `GET /orders/<int:order_id>/invoice`

**Confirmed by a real request** · severity estimate: critical · [CWE-78](https://cwe.mitre.org/data/definitions/78.html)

**Where:** `cakeshop/orders.py:45`

```

> 45 |     os.system(f"echo 'Order {order_id} | total {order['total']} UZS | {invoice_date()}' > {path}")
  46 |     return send_file(path)
```

**What is wrong:** Text the visitor controls is pasted into a shell command, so they can run their own commands on the server.

**Why the agent reports it:**
- **Flagged by:** bandit+semgrep (B605, dangerous-system-call, dangerous-system-call-audit, os-system-injection): start_process_with_a_shell
- **Checker (local model, 3/3 votes "real"):**
    - where the data comes from: user-written database content
    - how it reaches this line: Through the route parameter `order_id` and the `total` field fetched from the database.
    - what protects it: None visible in the code shown.
- 4 scanner warnings point at this problem and were merged into one.
- **Rule this route must follow:** format: The server must validate and sanitize the format to prevent malicious file format injection.
- **Which line enforces it?** None, according to the model: The code does not validate or sanitize the 'format' parameter, allowing for potential malicious file format injection.
- **Replay:** As bob (a normal user): `GET /orders/2/invoice` with a crafted `format` → `view raised FileNotFoundError after the command ran`.
- **Outcome:** a shell metacharacter payload ran a command (wrote a marker file) — command injection.

**How to fix:** Do not build shell strings. Call the program with a fixed argument list and `shell=False` (`subprocess.run([...])`), and allow-list any value that selects an option.

### 5. Access to another user's record (IDOR) on `GET /orders/<int:order_id>`

**What is wrong:** The route loads a record by the id in the request but never checks that it belongs to the logged-in user, so changing the id shows or changes someone else's data.

## What this report does not cover

routeguard looks at what scanners flag and at each route of the app. It does not yet examine code that runs outside routes (start-up settings, after-request hooks such as CORS or CSP headers, logging), and it does not check how passwords are stored unless a scanner flags a weak hash. Absence from this report is not proof that a problem is absent.
