## Problems

### 1. Access to another user's record (IDOR) on `GET /bookings/<int:rid>`

**Confirmed by a real request** · severity estimate: high · [CWE-639](https://cwe.mitre.org/data/definitions/639.html)

**Where:** `workshophub/bookings.py:28`

```
  26 | @bp.get("/<int:rid>")
  27 | @members_only
> 28 | def detail(rid):
  29 |     db = get_db()
  30 |     reservation = db.execute(
```

**What is wrong:** The route loads a record by the id in the request but never checks that it belongs to the logged-in user, so changing the id shows or changes someone else's data.

**Why the agent reports it:**
- **Rule this route must follow:** The booking detail can only be accessed by the user whose 'owner_id' matches the logged-in user's ID or by an administrator.
- **Which line enforces it?** None, according to the model: The @members_only decorator ensures that only authenticated users can access the route. However, it does not check if the logged-in user is the owner of the booking or an administrator.
- **Replay:** As bob (a normal user): `GET /bookings/1`, aiming at alice's reservations #1 → `200`.
- **Outcome:** bob read alice's reservations #1; response shows owner-only data 'confirmed'.

**How to fix:** Restrict the query to the current user (`... WHERE id = ? AND user_id = ?`) and return 404 when no row matches.

### CSRF: 3 state-changing route(s) accept forged requests

**What is wrong:** A request that changes data is accepted without an anti-forgery token, so another website can make a logged-in visitor's browser send it.

| Route | Status | Replay | Outcome |
| --- | --- | --- | --- |
| `POST /bookings/<int:rid>/cancel` | Confirmed by a real request | `POST /bookings/1/cancel` as bob → `302 -> /bookings/` | a forged POST with no token changed table reservations (302 -> /bookings/) |
| `POST /profile` | Confirmed by a real request | `POST /profile` as bob → `302 -> /profile` | a forged POST with no token changed table accounts (302 -> /profile) |
| `GET /logout` | Needs human review | `GET /logout` as anon → `302 -> /login` | the forged GET only rewrote the session cookie (302 -> /login): a real change (log in/out) or bookkeeping (a flash message, a token); keep for a human |

**How to fix:** Require a CSRF token on every state-changing form (e.g. Flask-WTF's `CSRFProtect`), use POST for changes, and set `SameSite=Lax` on the session cookie.
