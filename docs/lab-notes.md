# routeguard: lab notes

The full working log of the project: every step, every experiment (including the ones that failed), and
every number, in the order they were built. For a short overview start with the [README](../README.md);
for a step-by-step explanation read the [report](../report/routeguard_report.pdf). Paths below are
relative to the repository root, and "section N" refers to the sections of this file.

---

A security agent for Python/Flask web apps that runs on a **local model** (`qwen2.5-coder:7b` through
Ollama, on a MacBook Air M1 with 8 GB). It has three parts, built and measured one after another:

1. **Scanners + checker** (done): standard scanners find candidate bugs; fixed rules and the local model
   decide which warnings are real.
2. **Free-hunt baseline** (done): the local model looks for bugs by itself, with no scanner. This shows
   what the model can and cannot do alone.
3. **Route-by-route rule checking** (done): for each route, write down the rules it must follow,
   ask the model which line enforces each rule, and try to break the ones nobody enforces. Built for the
   bugs parts 1 and 2 miss: access control and business logic: route cards (section 8), the rules each
   route must follow (section 9), which line enforces each rule (section 13), and replaying each finding
   as a live request (section 14).

The results are written for a developer by `tools/report.py` into each app's `runs/report.md` (section 20).

The development target is `cakeshop/`, a small Flask app I wrote with **19 planted vulnerabilities** and
**8 decoys** (code that looks dangerous but is safe), listed in `cakeshop/labels/ground_truth.json`.
The pipeline was then run on apps I did not write:
[flask-webgoat](https://github.com/ShiftLeftSecurity/flask-webgoat) (`flask-webgoat/`, section 18) and
vulny-app, a logic-bug app generated by another AI model (section 19).

> All numbers come from single runs of a 7B model, on small apps, scored against answer keys I wrote.
> Treat them as indications, not proof. The prompts were developed on cakeshop only.

### Results at a glance

Full system = scanners + checker (`runs/merged.json`) together with the replayed rule findings
(`runs/replay.json`). Every finding was checked by hand against the code and the replay log; each hand
decision is in the app's `labels/hand_check.json` and `tools/score.py ... --hand` applies it. In brackets,
the automatic score, which only credits a finding within 2 lines of a labelled bug (section 6).
"Precision" is the share of findings that are real security problems (advisories for pinned versions count).

| App | Labels | Scanners + checker | Replay only | Full system: found (automatic) | Full system: precision (automatic) | Decoys flagged |
|---|---|---|---|---|---|---|
| cakeshop (mine, prompts tuned on it) | 19 bugs, 8 decoys | 11/19, 79% | 9/19, 100% | **17/19** (17/19) | **90%** (90%) | 1/8 |
| flask-webgoat (unseen, blind key) | 16 bugs, 0 decoys | 9/16, 91% | 6/16, 100% | **12/16** (11/16) | **94%** (76%) | - |
| vulny-app (generated, key unseen until after the run) | 8 bugs, 5 decoys | 0/8, 75% | 7/8, 64% | **7/8** (6/8) | **67%** (33%) | 0/5 |

- On cakeshop the route-by-route part adds the logic bugs the scanners cannot see (IDOR, mass
  assignment, missing admin check, negative quantity, CSRF), each confirmed by a real request.
- On flask-webgoat most bugs are code-pattern or configuration bugs, so scanners + checker do most
  of the work there. Replay adds CSRF on both, and on flask-webgoat it confirms the command injection by
  running a command. By hand, 6 of 6 flask-webgoat replay findings point at real bugs (the scorer credits 4:
  two sit more than 2 lines from the label anchor; section 18), but only 2 of the 6 were confirmed by an
  effect, the other 4 are kept as "uncertain" because replay has no payload for that sink.
- On vulny-app, built around the logic bugs Part 3 targets, everything comes from Part 3: 7 of 8 found,
  5 confirmed by a real request, every confirmed finding real, 0 of 5 decoys flagged (section 19).
- Replay is what keeps the rule step usable on new code: on flask-webgoat it cut 17 rule findings to 6,
  all on a real bug.
- The clearest limit: code outside routes (start-up settings, after-request hooks, logging) and password
  storage are never examined (report, section 13.3).

## 1. Pipeline

```
bandit, semgrep, pip-audit, gitleaks          -> raw/*.json  (4 different formats)
        |
tools/normalize.py                            -> findings.json   (one format, 42 warnings on cakeshop)
        |
agent/verify.py   (the checker)               -> runs/verified.json      (kept: real + uncertain)
        |                                        runs/verified_log.json  (every warning + verdict + reason)
tools/merge_findings.py                       -> runs/merged.json   (one item per problem)
        |
tools/score.py / tools/checker_eval.py        -> scores against the answer key

agent/hunt.py     (free-hunt baseline)        -> runs/hunt_file.json, runs/hunt_agent.json  (same format)
agent/routecard.py (part 3, step 1)           -> runs/routecards.json
agent/rules.py    (part 3, step 2)            -> runs/rules.json   (rules per route)
tools/rules_eval.py                           -> scores rules against labels/expected_rules.json
agent/enforce.py  (part 3, step 3)            -> runs/enforce.json   (findings, same format as findings.json)
                                                 runs/enforce_log.json (every rule: status, who decided, evidence)
agent/replay.py   (part 3, step 4)            -> runs/replay.json    (findings whose attack really works)
                                                 runs/replay_log.json (every finding: request, response, verdict)
```

| File | What it does |
|---|---|
| `run.sh` | Runs the whole pipeline on one app folder: `./run.sh cakeshop`. See section 16. |
| `tools/normalize.py` | Turns the JSON of the four scanners into one list with the same keys: tool, rule_id, title, file, line, snippet, severity, cwe, extra. Hides leaked secrets. |
| `agent/codeindex.py` | Reads the code with Python's `ast` (no model). Answers questions such as "which function contains line 40", "where is this name defined", "who calls this function". Never reads `labels/`, `raw/`, `runs/`. |
| `agent/llm.py` | Talks to Ollama. Every answer must match a JSON schema. Asks several times with different seeds and takes the majority. |
| `agent/verify.py` | The checker, see section 2. |
| `agent/hunt.py` | The free-hunt baseline, see section 5. |
| `agent/routecard.py` | Builds a factual card for every route (no model), see section 8. |
| `agent/rules.py` | Writes the rules each route must follow: 4 questions based on OWASP, see section 9. |
| `agent/enforce.py` | For each rule, the model says which line enforces it (or how to break it); code checks the cited line exists and belongs to the route, see section 13. |
| `agent/replay.py` | Runs each finding from step 3 as a real request with Flask's `test_client` and a set of users; keeps only the findings whose attack actually works, see section 14. No model. |
| `cakeshop/replay_config.json` | The only app-specific input to replay: app factory, database config key, writable dirs, login mechanism, and users with roles. A new target app ships its own. |
| `tools/rules_eval.py` | Scores a rules file against `labels/expected_rules.json` and writes a readable list of every rule. |
| `tools/merge_findings.py` | Merges warnings that point at the same problem, see section 3. |
| `tools/score.py` | Compares any findings file with the answer key: recall, precision, decoys flagged, missed bugs. `--strict` counts a hit only if the weakness type (CWE) also matches. |
| `tools/checker_eval.py` | Shows, warning by warning, what the checker kept or removed against the answer key, and which stage decided. |

## 2. How the checker decides (`agent/verify.py`)

Each warning goes through the cheapest step that can decide it:

1. **Dependency warning (pip-audit)** -> real. The version is in an advisory database.
2. **Evidence check** -> is the code the scanner quoted really at that line (within 2 lines)? If not, rejected.
3. Warnings on the same line are grouped; each line is checked **once**.
4. **Fixed rules, no model**:
   - an `import` line -> false alarm
   - a secret read from the environment -> false alarm; a secret written as a string -> real
   - MD5/SHA-1 used for passwords -> real
   - `debug=True` -> real
   - f-string SQL where every inserted name is checked against a fixed allow-list -> false alarm
5. **Local model**, for everything else. It sees the function around the flagged line (line marked `>>`) plus context:
   - the code of the function's own decorators (is the route protected?)
   - constants the function uses (allow-lists)
   - project functions called on the flagged line
   - functions that call this one (only if it has parameters)
   - for a template: the view that renders it and the code that stores the data it shows

   The scanner's own opinion is **not** shown. The model must answer, in this order:
   `source` (where the data comes from) -> `path` (how it reaches the line) -> `protection` -> `verdict`.
   3 votes, majority wins.
6. **Split vote** -> ask again with twice the context and 5 votes. Under 4 of 5 agreeing: `uncertain`, needs a human.

Real and uncertain warnings are kept; uncertain ones are kept so a person looks at them.

## 3. Merging duplicates (`tools/merge_findings.py`)

Scanners report one bug many times (bandit and semgrep on the same line, several semgrep rules,
8 advisories for one old Werkzeug). Two warnings are merged when:

- dependencies: same package
- code: same line, or same function and at most 2 lines apart **and** either the same kind of weakness
  (e.g. both SQL injection) or one line stores a variable the other line uses
  (`template = "..." + text` on one line, `render_template_string(template)` on the next)

Every merged item keeps the original warnings in `extra.merged_from`.

## 5. Free-hunt baseline (`agent/hunt.py`)

Question: what does the local model find **by itself**, with no scanner? This is the "just ask the
model" baseline that every other part should beat.

Two ways to hunt:

- `--mode file` (no scaffolding): the model sees each file (`.py`, templates, `requirements.txt`) with
  line numbers and lists every vulnerability. At a 4096-token window every cakeshop file fits whole.
- `--mode agent` (in the style of Vulnhuntr): the model starts from each of the 21 routes, sees the
  route's code and the names it uses that are defined elsewhere, and may ask to see up to 4 of those
  definitions per round, for up to 3 rounds, before it reports. Bugs outside routes (secret key, debug
  mode, dependencies) are out of reach by design.

The prompt names the general bug families (injection, access control, business logic, CSRF,
configuration) but nothing about cakeshop. The app has no comments that hint at the bugs.

The model must copy the line it reports. The copy is used to fix the line number (small models
miscount) and to catch made-up code; see section 6 for how it is matched.

### Results (one run each, temperature 0)

| | Scanners + checker | Hunt: file by file | Hunt: route by route |
|---|---|---|---|
| Bugs hit (within 2 lines) | 11/19 | 9/19 | 7/19 |
| Bugs hit, `--strict` (right weakness type) | 11/19 | 5/19 | 2/19 |
| Bugs found **for the right reason** (judged by hand) | 11 | **5** (+2 partly) | **1** (+2 partly) |
| Findings that hit a real bug | 79% per item | 34% (40% after merging) | 31% (25% after merging) |
| Decoys flagged | 1/8 | 2/8 | 4/8 |
| Made-up code in the copied line | - | 2 of 35 | 0 of 29 |
| Time | - | 9.4 min | 6.8 min |

Judged by hand, per bug:

- **Right:** file mode found V01 (SQL injection across two files), V04 (pickle), V13 (secret key),
  V14 (debug mode, which the scanners missed) and V15 (MD5). Route mode found V03 (path traversal,
  which the scanners also missed).
- **Partly right:** V02 was called XSS (it is template injection, which leads to code execution).
  V09 command injection was blamed on `order_id` and `order['total']`; the real source is the
  `?format=` parameter. The checker in section 2 made the same mistake.
- **Wrong reason (counted only by location):** V05 client-set price and V06 negative quantity were
  reported as "integer overflow / ValueError"; V08 IDOR as SQL injection on a parameterized query;
  V10 (an `/admin` route with no admin check, next to two routes that have one) as SQL injection;
  V12 open redirect as "session manipulation"; V19 CSRF had the right CWE but a meaningless
  explanation. V11 mass assignment was not found.

### What this shows

- **Logic bugs: 0 of 6 found for the right reason**, in either mode. The model recognises
  dangerous-looking code; it does not reason about who may do what.
- **Most false alarms follow three habits:** every SQL query is called SQL injection (including
  parameterized ones), every `{{ }}` in a template is called XSS (Jinja escapes them), and form fields in
  templates are called SQL injection. It missed the one real XSS (`|safe` in `product.html`) while
  flagging three other lines of the same file.
- **It does not tell decoys from bugs.** In route mode the path-traversal claim on V03 is word for word
  the same as on decoy D04, which is protected by `secure_filename`.
- **The "agent" never used its tool.** In 21 of 21 routes the model answered at once and never asked
  to see more code, so route mode was in practice a single look per route. That is why it missed V01:
  it never opened `search_products` in `db.py`. This matches the Vulnhuntr authors' note that open
  models do not handle their tool loop well.
- **Still useful as a complement:** it found V14 and V03, which no scanner flagged. Scanners + checker +
  those two would reach 13/19.

This agrees with published studies: models asked to judge code directly do close to chance on
realistic benchmarks (PrimeVul; Steenhoek et al., "To Err is Machine"), and change their answer when
variable names change (SecLLMHolmes, IEEE S&P 2024).

### Control: full route context, same open question (`--mode context`)

Added later, to separate the effect of the question from the effect of the context. For each route the model
gets the exact code bundle Part 3 uses (`rules.route_prompt`: route, decorators, called functions, constants,
before-request hook, template, table schema; all 21 prompts fit 4,096 tokens with nothing cut) and the same
"find the vulnerabilities" question. One run, temperature 0, 8.9 min.

| | By file | By route (agent) | Full context |
|---|---|---|---|
| Bugs hit (by location) | 9/19 | 7/19 | 10/19 |
| Found for the right reason (by hand) | 5 (+2 partly) | 1 (+2 partly) | 5 (+3 partly) |
| Logic bugs for the right reason | 0/6 | 0/6 | 1/6 (+1 partly) |
| Findings on a real bug | 34% | 31% | 34% |
| Decoys flagged | 2/8 | 4/8 | 5/8 |

- Context rescues the cross-file SQL injection (V01: `search_products` from `db.py` is now in the prompt).
- Logic bugs: V08 IDOR right; V10 partly ("query does not filter by user_id"); V05 and V06 reported as
  "non-integer value raises ValueError"; V11 and V19 not reported.
- More false alarms: D01 and D06 (allow-listed names) as SQL injection, D08 as XSS, D04 as path traversal, D03.
- Not comparable on V13, V14, V16-V18: the context never includes `run.py`, `__init__.py` or `requirements.txt`.
- Conclusion: the question explains most of the gap; the context explains the cross-file miss and one IDOR.

## 6. Measuring fairly: two fixes to the scoring

- **Matching the copied line.** The first version required an exact copy and marked 24 of 64 findings
  as made-up code. Checking them by hand: most were real lines re-typed with `'` instead of `"`, or a
  multi-line call written on one line. Matching now ignores spaces and quote style, accepts a statement
  spread over several lines and `...` in the copy, and accepts near copies (>= 85% similar). Only 2 of 64
  are really made up. This also recovered V04: file mode had found the pickle bug, 3 lines off.
- **`score.py --strict`.** The normal score counts any finding within 2 lines of a bug, even with the
  wrong explanation (V08 IDOR was "found" by a SQL-injection finding). `--strict` also requires the
  weakness type (CWE, or a related one) to match. It is a lower bound: it misses right answers with a
  wrong CWE number (V13 was reported as CWE-312, V14 as CWE-949). The hand judgement in section 5 sits
  between the two scores.

## 7. Next idea: check each route against rules it must follow

Parts 1 and 2 miss the same bugs: access control and business logic. These bugs are a **missing line**
(no ownership check, no admin check, a price taken from the client), so there is nothing dangerous to
spot. The fix is to ask a different question.

For each route:

1. **Write down what the route must guarantee**, e.g. "a user may only see their own order".
2. **Find the line that enforces each rule**, or say that none does.
3. **For a rule nobody enforces, describe a request that breaks it**, e.g. "log in as Bob, open Alice's order".
4. **Check the claim with code**: the cited line must exist and say what the model claims; later,
   replay the request on a local copy of the app with real users and see what comes back (section 14).

The model never searches for bugs. It answers small questions about 10-20 lines at a time, and code
checks its answers. This follows ABSENTIA (Duarte et al., 2026), where splitting the app into routes
raised recall from 3/30 to 18/30 and checking stated properties cut false reports by a third, and
Project Zero's Naptime principle that a finding should be verified by a tool, not by the model's
opinion.

To keep it general, the rules are not triggered by names (no "a field called `quantity`" or "a URL
starting with `/admin`"; that would be the rule-based discovery I removed in round 1, rebuilt). The
model gets the route's facts and a short list of rule **types** from public sources (OWASP API
Security Top 10, OWASP ASVS): who may call it, whose data it is, which values the server must not
trust, which values need limits, which fields the user must not change, CSRF on state-changing
requests. The model decides which apply and writes the concrete rule.

## 8. Step 1 done: route cards (`agent/routecard.py`)

Before the model is asked anything, plain Python builds a **route card**: only facts that can be read
from the code, no judgements. Nothing in it knows about cakeshop. The model never sees the card (it
gets the raw code, section 9); the code of the next steps decides what to ask, check and send from it.

| Part of the card | Used by | Example on cakeshop |
|---|---|---|
| request inputs (also inside helpers, `int()` conversion, loops over ALL form fields), SQL writes, tables and their columns | `rules.py`: one value question per client value | `/account` loops over every form field and runs `UPDATE users`, so each column of `users` becomes a value, and `is_admin` gets its own question (V11) |
| method, SQL writes, session changes | `rules.py`: CSRF rule, decided by code | `POST /checkout` + `INSERT orders` -> CSRF rule (V19) |
| other tables with a column named like the route's data | `rules.py`: their `CREATE TABLE` goes into the prompt | `/checkout` sends `price`; `products` stores `price` (V05) |
| decorators (and the ones they wrap), called functions, constants, before-request hooks | `enforce.py`: is the line the model cites really part of this route? | `/admin/orders` has no decorator, so `g.user['is_admin']` (inside `admin_required`) does not count as its protection (V10) |
| URL parameters, tables with an owner column (`user_id`, ...) | `replay.py`: bob asks for alice's record | `/orders/<order_id>` reads `orders`, which has `user_id` -> bob opens alice's order (V08) |
| form fields, checks inside decorators, the current user | `replay.py`: which fields to send, who has to log in | `/checkout` needs a login; `quantity=-5` is stored as a negative total (V06) |
| places where the word "csrf" appears | `replay.py`: no token mechanism at all | none in cakeshop (V19) |

`python3 ../agent/routecard.py /checkout` prints one card; `runs/routecards.json` has all of them. A
self-check finds every `request.*` read in the project; **0** are missing from the cards on cakeshop.

Until round 3 the card was also written out as text for the model, with extra parts only the model
used (every `if` in the route, which fields a page shows, the decorators of neighbouring routes). Those
were removed with the text (section 10).

Known gaps: SQLAlchemy/ORM models, class-based views, `add_url_rule`, helpers called as methods.
Tables are matched to route data by column name only.

## 9. Step 2 done: the rules each route must follow (`agent/rules.py`)

The model is asked what each route **should** guarantee, not whether the code does it (that is step 3).
It took three rounds to get a format a 7B model handles well.

### The 4 questions (round 3, kept)

They cover only what scanners cannot see, and use OWASP's own categories:

| Question | Asked how | OWASP |
|---|---|---|
| Q1 Who may call this route? `anyone` / `logged_in_user` / `admin` | model, once per route; code writes the rule sentence | Top 10 A01 Broken Access Control; API5 Broken Function Level Authorization |
| Q2 Whose record is it? (the table stores who owns the row) | model, once per route | API1 Broken Object Level Authorization (IDOR) |
| Q3 Does it change state? -> needs CSRF protection | **code**: a non-GET method, an INSERT/UPDATE/DELETE, or a session change | A01 (CWE-352) |
| Q4 For **each value** the client sends: content / picks a record / server must decide / needs limits / client must not set | model, one required answer per value | API3 Broken Object Property Level Authorization (mass assignment); A04 Insecure Design |

Each value in Q4 is shown with the lines where it ends up, read from the code with `ast`, for example:

```
VALUE price: request.form['price'], converted with int()
   125 |     price = int(request.form["price"])
   126 |     total = price * quantity
   128 |     cur = db.execute(
   129 |         "INSERT INTO orders (user_id, product_id, quantity, total, message, note) ...
   134 |             total,
```

A loop over all form fields (`for key, value in request.form.items()`) becomes one value per column of
the table it writes to, so `is_admin` gets its own question. The model is told to judge from what the
route is for (URL, data, page), not from the decorators and checks already in the code.

### How the format changed, and why

| Round | Format | Rules needed for labelled bugs | Expected rules written | Extra rules | CSRF on POST / GET-only routes |
|---|---|---|---|---|---|
| 1 | free list of 6 rule types, card + code | 6/9 | 84% | 35 of 92 | 3/7 and 8/14 |
| 1 | same, raw code only | 8/9 | 92% | 27 of 84 | 5/7 and 5/14 |
| 1 | same, card + full code | 7/9 | 88% | 35 of 92 | 4/7 |
| 2 | yes/no checklist per type, card + code | 7/9 | 88% | 5 of 38 | 7/7 and 0/14 |
| 2 | same, raw code only | 6/9 | 88% | 8 of 43 | 7/7 and 0/14 |
| **3** | **4 OWASP questions, one answer per client value** | **8/9** | **92%** | **6 of 39** | 7/7 (by code) |
| 3, final | same, raw code only (the pipeline as submitted, re-run 2026-10-05) | 8/9 | 92% | 5 of 38 | 7/7 (by code) |

"Rules needed for labelled bugs" = the rule the next step needs to catch V05, V06, V08, V10, V11, V12,
V19 (CSRF on most POST routes) or to judge the decoys D05 and D07 (`tools/rules_eval.py`, key in
`labels/expected_rules.json`, my judgement). One run each, temperature 0.

- **Round 1, free list:** the model filled every type. 30 of the 35 extra rules were sentences like
  "this route does not require CSRF protection". It also described the current code ("because: no
  decorators") instead of the intended rule, most often when it saw the card (14 times vs 3 with code
  only), whose "Decorators: none" lines seem to pull it towards describing the code.
- **Round 2, yes/no checklist:** filler gone, CSRF exactly right. But the value rules were skipped
  ("limits" said yes once in 21 routes), the reason often repeated the question, rules shrank to single
  words (`['price']`), and the login `next` redirect was missed in all 5 runs of rounds 1-2.
- **Round 3, 4 questions:** asking about each value separately found `next` (V12) for the first time,
  separated `is_admin` (must not set) from `email`/`address` (content) on `/account` (V11), and as a
  side effect flagged the values behind three code-pattern bugs: `format` (V09 command injection),
  `name` on `/image` (V03 path traversal) and the `cart` cookie on `/cart/add` (V04 pickle).
- **Card vs raw code:** the order flipped between rounds 1 and 2 (code ahead, then card ahead), with
  gaps of 1-2 items in single runs. No conclusion. The round-3 numbers above were measured with the
  card + the route's code; the pipeline now gives the model only the raw code (one view of a route,
  the same one step 3 uses). Re-run with raw code only ("3, final"): the same 8/9 and 92%, one extra
  rule fewer.

### What is still wrong (left as is)

- **V05 missed:** `price` was called "needs limits" ("price must be a positive integer"), which would
  not catch a price of 1. The value question did not say that `products.price` already stores it; the
  card knows this but it is not passed to Q4. On `/checkout` the model also copied the category
  definitions back as its reasons.
- **Inconsistent:** the same cart cookie is "content" on `/cart` and "server must decide" on
  `/cart/add`; `name` is "picks a record" on `/thumbnail` and "server must decide" on `/image`.
- **"Whose record" is too broad:** yes on `/register`, `/login` and `/cart/add` (there is no cart table).
- **Single run:** answers may change between runs.

I stopped tuning the prompts here on purpose: every further fix found by looking at cakeshop's answer
key makes the numbers less trustworthy. Wrong rules (such as "whose record" on `/login`) should turn
into "enforced / not applicable" in step 3 rather than into findings.

## 12. Known limitations

- Prompts and rules tuned on one app I wrote; two unseen apps since then (sections 18-19), both small
  and deliberately vulnerable. Single runs, so a few verdicts can flip between runs.
- Checker context: when a function has many callers, all are added and the last ones are cut when the
  prompt is full; the dangerous caller may be cut. Callers are followed only one level up. Decorators
  of callers and library decorators are not shown.
- Merging is a guess from location and data flow; on a large codebase two different bugs on nearby
  lines could be merged if they are the same kind of weakness.
- Scoring by location can credit a finding with the wrong explanation; `--strict` can miss a right
  finding with a wrong CWE number. Section 5 is judged by hand for that reason.

## 13. Step 3: which line enforces each rule? (`agent/enforce.py`)

For each rule from section 9, the model gets the rule and the code that runs for the route (route,
decorators, called functions, before-request hook, template, table; for a value rule also the lines where
the value goes) and answers:

- **enforced**: copy the line that enforces the rule
- **not enforced**: copy the line where the rule is broken, and describe a request that breaks it
- **not applicable**: the rule does not fit the route (step 2 writes some wrong rules)

Step 2's "why the rule applies" is not shown: it often describes the code wrongly ("it filters by user_id"
on the route that does not), which would answer the question for the model.

**Code checks an "enforced" answer**, without knowing any library:

1. the copied line exists in the project (line numbers the model copied from the prompt are removed first)
2. it is part of the code that runs for this route: the route, a function it calls, one of its decorators,
   or a constant it uses. A copied `@decorator` counts if it decorates this route (the model often gives the
   file where the decorator is defined).

If either fails, the answer becomes **uncertain** and is kept as a finding. Example: on `/admin/orders`
(V10, no protection at all) the model said "enforced" and copied `g.user['is_admin']`; that line is in
`admin_required`, which this route does not use, so V10 stays a finding.

Code does **not** judge whether the cited line really enforces the rule. `if key in USER_COLUMNS:` passes
as the protection of `is_admin`, although `is_admin` is in that list (V11). A "not enforced" answer is not
checked either; replaying the attack (section 14) is what tests both.

Findings use the format of `findings.json`: the line the model copied if it is in the route's code, else
the route's `def` line; the CWE from the rule type (whose data CWE-639, CSRF CWE-352, must not set CWE-915,
limits CWE-1284, admin-only CWE-862, login-only CWE-306), and the model's own CWE for "do not trust".

## 14. Step 4 done: replay the attacks (`agent/replay.py`)

Step 3 keeps a rule as a finding when the model says no line enforces it, or when its "enforced" answer
does not check out. A missing control and a wrong rule look the same there. This step turns each finding
into a real request against the app with Flask's `test_client` and the three seed users (admin, alice,
bob), and keeps only the findings whose attack actually works. It uses no model.

There is one replay helper per rule **type**, not one per bug, so nothing in it is specific to cakeshop:

| Rule type | The request it sends | Confirmed when | Dropped when |
|---|---|---|---|
| who_may_call | a caller below the required level opens the route (a normal user for an admin route, logged-out for a login route) | the response shows the victim's stored data (their user row or rows they own) | 403 / redirect to login / 404, or a page with no one's private data |
| whose_data | bob opens a record owned by alice (an id in the URL, a table with a per-user owner column) | bob's response shows alice's owner-only data | bob gets 403/404, or the route has no record id / no owner column (does not apply) |
| limits | the value is sent out of range (-5) | the server stores it (e.g. a negative total) | the server rejects it (400) |
| must_not_change | a normal user posts the forbidden field (`is_admin=1`) | that user's own row changes | the field is ignored |
| do_not_trust | a payload for the sink the value reaches (external URL, `../` path, `{{7*7}}`, a crafted cookie, a shell metacharacter), each proven by its own effect | the effect happens (off-site redirect, source code returned, `49`, a marker file) | no effect |
| csrf | the state-changing request with no token | the project has no token mechanism at all | the request is refused for a reason another site cannot get around (401/403/405/415: login, API key header, JSON), or a token mechanism rejects it |

The `whose_data` helper runs for **every** whose_data rule, including the ones step 3 accepted as
"enforced" -- that is where a wrong "enforced" verdict is caught. The deserialisation and command
payloads only create one empty marker file; the target is the deliberately vulnerable app on 127.0.0.1.

Everything app-specific lives in one file, `replay_config.json`, next to the app: how to import and
start it, which config key holds the database, the users table and username column to resolve accounts,
which directories the test run may write to, and the users with their roles (`admin`, `attacker`,
`victim`) and how to log in. The replay logic reads only that, so a second app needs a new config, not a
code change. Every tool that attacks a running app needs these facts; keeping them in one small file is
the point, not a gap. The access level a route enforces is read from the *checks inside its decorators*
(an `is_staff` test, say), not their names, so a decorator named `@staff_only` is recognised like
`@admin_required`.

## 16. How to run

Requires the scanners (`requirements-agent.txt`, installed in `agentenv/`), gitleaks on PATH, Ollama with
`qwen2.5-coder:7b`, and an environment with the app's own dependencies for replay (`appenv/`). The agent
code itself uses only the Python standard library.

```bash
python3 -m venv agentenv && agentenv/bin/pip install -r requirements-agent.txt   # once
python3 -m venv appenv && appenv/bin/pip install -r cakeshop/requirements.txt    # replay deps, per app
ollama pull qwen2.5-coder:7b
./run.sh cakeshop
```

`rerun.sh` re-runs every step after the scanners and copies the outputs to `runs/<tag>/`; with
`AGENT_TEMP`/`AGENT_SEED` set it makes sampled repeat runs.

`run.sh` runs the steps below in order. Each step can also be run alone from the app folder; every step
reads and writes fixed files:

```bash
cd cakeshop
python3 ../tools/normalize.py             # raw/*.json -> findings.json
python3 ../agent/verify.py                # findings.json -> runs/verified.json (+ _log)
python3 ../tools/merge_findings.py        # runs/verified.json -> runs/merged.json
python3 ../agent/hunt.py --mode file      # baseline -> runs/hunt_file.json  (or --mode agent / --mode context)
python3 ../agent/routecard.py             # runs/routecards.json  (routecard.py /checkout prints one card)
python3 ../agent/rules.py                 # runs/rules.json (+ _log)
python3 ../agent/enforce.py               # runs/rules.json -> runs/enforce.json (+ _log)
../appenv/bin/python ../agent/replay.py   # runs/enforce.json -> runs/replay.json (+ _log)

python3 ../tools/score.py runs/replay.json --strict          # against labels/ground_truth.json
python3 ../tools/score.py runs/merged.json runs/replay.json  # several files scored as one
python3 ../tools/checker_eval.py          # what the checker kept or removed, warning by warning
python3 ../tools/rules_eval.py            # runs/rules.json against labels/expected_rules.json
```

The model and its settings are constants at the top of each file (`MODEL` in `agent/llm.py`).

`cakeshop/` is deliberately vulnerable: run it only on 127.0.0.1 and never expose it to a network.

## 20. The readable report (`tools/report.py`)

The pipeline's outputs are JSON. `tools/report.py` (run by `run.sh` and `rerun.sh` after replay) writes
`runs/report.md` for a developer. It makes no new decision; it explains the saved ones:

- **Where**: file, line, route, and a code excerpt.
- **What is wrong**: the weakness in plain words, with a severity estimate from the weakness type alone.
- **Why the agent reports it**: the scanner and the checker's verdict (fixed rule, advisory, or the model's
  source / path / protection and its votes), or the rule the route breaks and the model's reading of the code.
- **Evidence**: the request replay sent, as which user, and what changed.
- **How to fix**: a concrete fix for that weakness type.

Findings on the same problem are shown once (a scanner finding absorbs the rule findings on the same lines, and
scanner findings with the same weakness within 5 lines, such as `pickle.loads` and `pickle.dumps` of one cookie, are
shown as one; two rule findings are never merged, since each is one rule on one route). CSRF findings are collected in one table,
outdated libraries in another, and a last section lists the suspicions replay tested and cleared. When an untested
finding's weakness label came from the model (it once called a client-sent total "command injection"), the report
describes it by the rule it breaks instead.

## 21. Agent mode: the model designs each test (`agent/investigate.py`)

Replay derives every test parameter in code. Agent mode hands that choice to the model: for each rule enforce.py
marks as broken (and every whose-data rule), the model picks the caller, the field, the bad value and, for
"do not trust" rules, the kind of probe (shell, path, deserialise, template). The judging stays in code: the same
oracles as replay decide whether the test proved anything. For dangerous probes the model only names the kind and
the code supplies the same harmless payloads replay uses. Output: `runs/investigate.json` and
`runs/investigate_log.json`; `tools/compare_modes.py` lines up the two modes rule by rule.

Run on vulny-app, the same 27 rules as replay, one run:

| | Replay (code designs the test) | Agent mode (model designs the test) |
|---|---|---|
| Bugs found (hand-checked) | 7/8 | 4/8 |
| Bugs confirmed by a real request | 5 (V02, V03, V05, V07, V08) | 4 (V02, V03, V07, V08) |
| Precision (hand-checked) | 64% | 75% |
| False confirmations | 0 | 0 |
| Rules: confirmed / dropped / uncertain / not applicable | 7 / 3 / 7 / 10 | 6 / 9 / 2 / 10 |

- The two agree on 21 of 27 rules. Every confirmation by the agent is also a replay confirmation; replay confirms
  one more.
- **V05 lost to a bad value.** Asked for an out-of-range seat count, the model chose `:999999` ("a string that does
  not represent a valid non-negative integer"). The server never stored it, so the rule was dropped. Replay sends -5
  and the server stores it.
- **V04 and V06 lost to the wrong probe.** For the client-sent `total_cost` and for `credit_balance` the model chose a
  template-injection probe (for `credit_balance` its own reason said "SQL injection"). `{{7*7}}` was not evaluated,
  or the request crashed on a NOT NULL constraint, and both rules were dropped. Replay has no test for these value
  kinds and keeps them as uncertain, so they reach a human; in agent mode they disappear.
- V01 is missed by both: the rules step judged the staff page open to any member, so neither mode tests it.

**Conclusion.** The model's test design never produced a false confirmation, but it fails quietly: a bad value or the
wrong probe turns a real bug into "safe". With a 7B model the tests stay designed in code. Agent mode is worth using
only where replay has no test, with its "safe" verdicts kept for a human instead of dropping the finding.

One harness bug was fixed before this run: agent mode first took the access level a route *enforces* from its code,
instead of the level the rules step says it *should* require (as replay does), so a route with no login check at all
was skipped as public. With the fix it confirms V02 like replay.
