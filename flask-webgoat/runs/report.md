## Problems

### 1. OS command injection on `GET /grep_processes`

**Confirmed by a real request** · severity estimate: critical · [CWE-78](https://cwe.mitre.org/data/definitions/78.html)

**Where:** `flask_webgoat/actions.py:42`

```
  40 | def grep_processes():
  41 |     name = request.args.get("name")
> 42 |     res = subprocess.run(
  43 |         ["ps aux | grep " + name + " | awk '{print $11}'"],
  44 |         shell=True,
```

**What is wrong:** Text the visitor controls is pasted into a shell command, so they can run their own commands on the server.

**Why the agent reports it:**
- **Flagged by:** bandit+semgrep (B602, dangerous-subprocess-use, subprocess-injection, subprocess-shell-true): subprocess_popen_with_shell_equals_true
- **Checker (local model, 3/3 votes "real"):**
    - where the data comes from: HTTP query/form/cookie/header
    - how it reaches this line: HTTP query parameter 'name'
    - what protects it: none
- 4 scanner warnings point at this problem and were merged into one.
- **Rule this route must follow:** name: The 'name' parameter must be sanitized to prevent command injection attacks.
- **Which line enforces it?** None, according to the model: The 'name' parameter is directly concatenated into the command string without sanitization, making it vulnerable to command injection attacks.
- **Replay:** As a logged-out visitor: `GET /grep_processes` with a crafted `name` → `200`.
- **Outcome:** a shell metacharacter payload ran a command (wrote a marker file) — command injection.

**How to fix:** Do not build shell strings. Call the program with a fixed argument list and `shell=False` (`subprocess.run([...])`), and allow-list any value that selects an option.

### 2. Insecure deserialisation on `POST /deserialized_descr`

**Judged real by the checker (not tested)** · severity estimate: critical · [CWE-502](https://cwe.mitre.org/data/definitions/502.html)

- **Which line enforces it?** None, according to the model: The code uses the `pickle` module to deserialize data directly from the user input without any validation or sanitization.

- **Outcome:** the value reaches a sink this replay does not model; keep for a human.

**How to fix:** Never `pickle.loads` data that came from a client. Store the data server-side (session or database) or use JSON, and sign anything that must round-trip through the client.

### 3. Code injection / debug console

> 12 |     app.run(debug=True)

### 5. SQL injection on `POST /login`

**Where:** `flask_webgoat/auth.py:17`

> 17 |     query = (
  18 |         "SELECT id, username, access_level FROM user WHERE username = '%s' AND password = '%s'"

**What is wrong:** Visitor input is pasted into an SQL string, so it can change the query: read other tables, bypass a login, or modify data.

**Why the agent reports it:**
- **Flagged by:** bandit+semgrep (B608, tainted-sql-string): Detected user input used to manually construct a SQL string. This is usually bad
- **Checker (local model, 3/3 votes "real"):**

    - what protects it: None
- 2 scanner warnings point at this problem and were merged into one.
- **Rule this route must follow:** password: The server must verify the password against the stored hash to ensure the user is authenticated.
- **Which line enforces it?** None, according to the model: The password is being directly inserted into the SQL query without any form of hashing or verification.
- **Replay:** As bob (a normal user): `POST /login` with a crafted `password` — not sent, replay has no test for this kind of value yet.
- **Outcome:** the value reaches a sink this replay does not model; keep for a human.

**How to fix:** Use parameterised queries (`db.execute('... WHERE name LIKE ?', (f'%{term}%',))`); never format input into SQL text.

### CSRF: 1 state-changing route(s) accept forged requests

**What is wrong:** A request that changes data is accepted without an anti-forgery token, so another website can make a logged-in visitor's browser send it.

| Route | Status | Replay | Outcome |
| --- | --- | --- | --- |
| `POST /login` | Needs human review | `POST /login` as bob → `200` | the forged POST only rewrote the session cookie (200): a real change (log in/out) or bookkeeping (a flash message, a token); keep for a human |

**How to fix:** Require a CSRF token on every state-changing form (e.g. Flask-WTF's `CSRFProtect`), use POST for changes, and set `SameSite=Lax` on the session cookie.

## What this report does not cover

routeguard looks at what scanners flag and at each route of the app. It does not yet examine code that runs outside routes (start-up settings, after-request hooks such as CORS or CSP headers, logging), and it does not check how passwords are stored unless a scanner flags a weak hash. Absence from this report is not proof that a problem is absent.
